# 마이페이지·온보딩·컬렉션 인수인계

작성일: 2026-10-14 · 로컬 dev 작업 · 운영 배포·운영 DB 변경은 수행하지 않음

## 완성된 사용자 흐름

- 상단 계정 버튼 → `/mypage`. 내 컬렉션 / 내 감상·비평 / 활동 기록 / 좋아요한 그림 / 설정을 제공합니다.
- 첫 로그인 → 생년월일(선택), 대화 스타일의 2단계 온보딩. 건너뛰면 기본 설정으로 완료하며 계정에 완료 상태가 저장됩니다.
- 설정에서 생년월일을 입력·삭제하고, 말투를 easy 또는 professional로 바꿉니다. 설명 주제의 고정 순위는 받지 않습니다.
- 실제 모드는 서버 저장입니다. 기존 나이대·성별 브라우저 프로필을 자동 업로드하거나 생년월일로 추정하지 않습니다. 미리보기는 브라우저의 계정별 저장입니다.
- 내 감상·비평은 기존 다이어리의 같은 데이터입니다. 비공개 글은 본인에게만 보이고 ‘이어 쓰기’는 해당 날짜의 캘린더·다이어리를 엽니다.
- 컬렉션 생성·제목/소개 수정·삭제, 작품 검색·담기·꺼내기, 작품 상세의 ‘내 컬렉션에 담기’를 연결했습니다. 컬렉션은 비공개이며 작품 중복 추가는 무해합니다.
- 컬렉션 채팅은 생성 또는 담기 요청을 분석하고, 정확한 작품·컬렉션을 제안합니다. 사용자가 확인 버튼을 눌러야 저장합니다. 작품이 모호하면 재질문합니다.
- AI 취향 소개는 본인의 좋아요·컬렉션 작품(중복 제거, 최대100점)의 제목·작가·연도를 사용합니다. 생년월일, 이메일, UID, 다이어리 본문을 AI에 전송하지 않습니다. 제공하지 않은 기법·성격·연령 등을 추론하지 않도록 지시합니다.
- 도슨트 POST의 분류 → 승인 문서 검색 → 생성 → 검증된 출처 → 로그인 사용자 대화 저장을 연결했습니다. 말투만 개인화하고 설명 주제는 질문에 맞춥니다. 출처 없는 답은 거절합니다.

## 데이터와 성능

Alembic head는 `20261014_0008`입니다. 기존 0007 다이어리 위에 `user_preferences`의 생일·말투·온보딩 완료·취향 소개 캐시 등을 추가하고, `collections`·`collection_items`를 생성합니다. 0008에 포함된 `explanation_priorities` 컬럼은 호환을 위해 남지만 새 프로필 API와 도슨트는 읽거나 갱신하지 않습니다. 모델과 새 ERD는 20개 서비스 테이블입니다. `01_schema_mvp.sql`은 0006 스냅샷이므로 신규 설치에도 전체 Alembic 이력을 사용합니다.

컬렉션 목록은 50개 이내, 미리보기 3점이며 일괄 조회합니다. 작품/비평은 12개, 활동은 20개씩 더 불러옵니다. 좋아요 화면도 12개씩 표시합니다. 새 화면에는 반복 애니메이션이나 전체 카드의 실시간 블러를 추가하지 않았습니다. 취향 소개는 자동 생성하지 않고 같은 근거의 결과를 재사용합니다. 계정 전환 시 개인 요청의 늦은 응답을 버리고 개인 화면·대화·폼을 닫거나 초기화합니다.

활동 기록은 현재 남아 있는 좋아요·일별 열람·다이어리·컬렉션의 최신 상태입니다. 삭제 전 모든 행동을 영구 보존하는 감사 로그는 아닙니다. 활동 페이지의 offset 방식은 조회 중 새 활동이 추가되면 경계가 변할 수 있습니다. 새로고침으로 최신 목록을 다시 볼 수 있습니다.

## MCP

공식 [Python SDK v1](https://github.com/modelcontextprotocol/python-sdk/tree/v1.30.0)의 stateless Streamable HTTP를 `/mcp/`에 제공합니다. 앱의 채팅은 불필요한 서버 간 왕복 없이 REST를 사용하고, 외부 MCP 클라이언트는 같은 저장 서비스를 호출합니다.

| 도구 | 인자 | 동작 |
| --- | --- | --- |
| list_collections | 없음 | 본인 컬렉션·개수·미리보기 |
| search_artworks | query | 공개 카탈로그에서 작품·작가 검색, 최대8점 |
| create_collection | name | 본인 비공개 컬렉션 생성 |
| add_artwork_to_collection | collection_id, artwork_id | 소유권·작품 존재 확인 후 중복 없이 담기 |

모든 요청에 `Authorization: Bearer <Firebase ID token>`을 사용합니다. 클라이언트는 토큰을 안전하게 보관하고 Firebase SDK로 갱신해야 합니다. user_id를 도구 인자로 받지 않습니다. 별도 OAuth 동적 등록·로그인 화면은 제공하지 않습니다. 외부 클라이언트가 임의의 인증 방식을 자동으로 사용할 수 있다는 의미는 아닙니다. 생성·담기 도구는 해당 작업을 사용자가 요청했을 때 호출하도록 설명·annotation을 제공합니다.

호스트·Origin 검증을 유지합니다. 운영에서는 `MCP_ALLOWED_HOSTS`에 실제 API 호스트(스킴·경로 제외)를 추가하고, `CORS_ORIGINS`에 프론트 Origin을 설정해야 합니다. 기본값은 localhost만 허용합니다. SDK 관리자는 FastAPI lifespan에서 시작·종료하며 재시작 시 새 관리자를 만듭니다.

## 운영 담당자가 반영할 순서

1. 이 코드와 잠금 파일로 서버 의존성을 설치합니다 (`uv sync --frozen`).
2. 운영 DB 백업·현재 revision 확인 후 `alembic upgrade head`로 0007과 0008을 순서대로 적용합니다. 이번 작업에서는 오프라인 SQL 생성만 했습니다.
3. 서버 전용 `OPENAI_API_KEY`, `ASSISTANT_MODEL`(기본 gpt-4.1-mini), 기존 Chroma/임베딩 설정을 확인합니다. 키는 프론트 빌드에 넣지 않습니다.
4. 운영 담당자가 `AUTH_MODE=firebase`, 프로젝트 ID `skn35-3rd-1team`, Admin 인증 정보와 CORS를 확인합니다. dev 모드는 사용자 계정이 합쳐지는 개발용 설정입니다.
5. MCP를 원격 사용한다면 실제 API Host를 `MCP_ALLOWED_HOSTS`에 추가합니다. 사용하지 않으면 로컬 허용 기본값을 유지할 수 있습니다.
6. 백엔드 배포 후 프론트를 `ARTLOG_DEMO=false`, 기존 `API_BASE_URL`과 Firebase 설정으로 빌드·배포합니다.
7. 서로 다른 두 실제 계정으로 설정 저장·다른 브라우저 복원, 비공개 비평 분리, 컬렉션 분리, 실제 AI 소개/채팅/도슨트와 출처 품질을 확인합니다. 운영 토큰을 로그·문서·채팅에 남기지 않습니다.

AI 연결이 없으면 503으로 안내하며 직접 컬렉션 편집은 사용할 수 있습니다. 미리보기에서는 실제 AI를 호출하거나 준비된 글을 실제 AI 생성 결과처럼 표시하지 않습니다. 실제 운영 DB·Firebase·유료 모델·Chroma를 함께 연결한 통합 검증은 이번 로컬 검증 범위에 포함하지 않았습니다. Railway 설정은 변경하지 않았습니다.

## 검증

격리 SQLite에서 실제 HTTP·SQL로 프로필 순서·날짜 검증, 두 사용자 분리, 컬렉션 CRUD·중복 담기·목록 페이지, 내 비평·활동·취향 근거, 채팅 확정 전 무변경을 검증했습니다. 실제 MCP initialize / tools/list / tools/call 전송도 테스트했고, 다른 계정 컬렉션 접근을 거절했습니다. 기존 Firebase 서명 검증 테스트는 그대로 유지했습니다. 모델 생성은 가짜 응답으로 검사하며 유료 API를 호출하지 않았습니다.

Flutter에서는 서버 계약, UID별 컬렉션 보관, 늦은 프로필 응답 폐기, 320/1280px 설정·순서 변경·저장, 실제 화면의 컬렉션 생성·검색·담기, 3단계 온보딩·건너뛰기·계정 전환을 검사합니다. 최종 실행 결과와 브라우저 화면은 `frontend/verification/mypage/`에 기록합니다.

최종 결과: Flutter 98개·백엔드 308개 통과, Flutter 분석·Ruff·공백 검사 통과, release 웹 빌드 성공. 실제 브라우저 컬렉션 저장·새 탭 복원·설정 변경과 모바일 화면을 확인했습니다. [검증 기록과 화면](../frontend/verification/mypage/README.md)을 참고합니다.
