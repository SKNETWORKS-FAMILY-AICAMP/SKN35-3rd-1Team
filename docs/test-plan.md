# 테스트 계획

## 목적

RAG 답변이 선택한 작품과 저장된 문서 범위 안에서만 생성되는지 확인하고, 좋아요·팔로우·열람 기록이 ERD와 API 약속대로 동작하는지 검증한다. 실제 LLM 품질 평가는 자동 테스트와 분리한다.

## 지금 준비된 입력

- RAG 평가 질문 30개: `backend/tests/questions/rag-eval.json`
- 가짜 챗봇 응답: `backend/tests/fixtures/chat-responses.json`
- 사용자 활동 계약 사례: `backend/tests/contracts/activity-cases.json`
- 위 파일의 형식 검사: `backend/tests/test_evaluation_fixtures.py`

질문셋은 사실 확인형 10개, 세부 관찰·해석형 8개, 비교형 4개, 범위 밖 3개, 근거 부족형 3개, 멀티턴형 2개로 구성한다.

## RAG 평가 항목

| 지표 | 계산 | 1차 목표 |
| --- | --- | --- |
| 검색 근거 적중률 | 기대 `target_doc_keys` 중 하나 이상이 검색된 질문 / 검색 대상 질문 | 90% 이상 |
| 범위 밖·근거 부족 거절률 | `refused: true` 기대 질문 중 실제 거절한 질문 / 전체 거절 기대 질문 | 100% |
| 정상 질문 응답률 | `refused: false` 기대 질문 중 답변한 질문 / 전체 정상 질문 | 90% 이상 |
| 출처 포함률 | `source_required: true` 질문 중 출처가 있는 답변 / 전체 해당 질문 | 100% |
| 출처 정합률 | 반환 출처가 실제 검색 청크의 문서에 속하는 수 / 전체 반환 출처 | 100% |
| URL 유효성 | HTTP 2xx 또는 정상 리다이렉트인 고유 출처 URL / 전체 고유 URL | 95% 이상 |
| 금지 주장 발생 | `forbidden_claims`를 사실로 단정한 답변 수 | 0건 |
| 멀티턴 맥락 유지 | 대명사·생략 표현의 대상을 올바르게 이어간 질문 / 멀티턴 질문 | 100% |

키워드는 보조 신호다. 표현이 달라도 의미가 맞을 수 있으므로 최종 답변 품질은 사람이 확인한다.

## 실행 단계

1. `pytest backend/tests/test_evaluation_fixtures.py`로 평가 자료 자체를 검증한다.
2. RAG 구현 후 각 질문에 대해 검색된 `doc_key`, 거리, 답변, `refused`, 출처를 저장한다.
3. 자동 집계로 거절·출처·검색 지표를 계산한다.
4. 세부 해석형과 멀티턴형은 사람이 근거 문서와 답변을 대조한다.
5. 결과와 실패 원인을 `docs/test-result.md`에 기록한다.

## 사용자 활동 기능의 핵심 확인 사항

- 좋아요·팔로우 `PUT`/`DELETE`는 여러 번 호출해도 최종 상태가 같다.
- 활동 목록은 로그인한 사용자 본인의 데이터만 반환한다.
- 같은 날 같은 작품을 다시 보면 새 행 대신 `view_count`가 증가한다.
- `viewed_on`은 서버에서 `Asia/Seoul` 기준으로 계산한다.
- 월별 캘린더의 `artwork_count`와 `total_views`를 구분한다.
- 날짜 경계와 월 경계 데이터를 각각 확인한다.

서비스와 API가 생기면 `activity-cases.json`의 각 항목을 가짜 repository 기반 서비스 테스트와 FastAPI 테스트 클라이언트 기반 API 테스트로 옮긴다. TiDB 전용 SQL은 별도 테스트 DB에서만 확인한다.
