# 도슨트 프롬프트 정확도 평가 절차

## 범위와 판정 단위

- 기본 질문셋은 [`rag-eval.json`](../backend/tests/questions/rag-eval.json) 30문항이다. 검색 적중, 범위 밖 거절, 일반 답변, 멀티턴을 기존 [`test-plan.md`](test-plan.md)의 지표로 평가한다.
- 추가 질문셋은 [`prompt-accuracy.json`](../backend/tests/questions/prompt-accuracy.json) 9문항이다. 근거 부족 유보, 일부 답변, 동명 작품 판본, 보정문, 팀 감상 포인트, 출처 ID, 원문 장문 복제, 이전 답변 정정을 집중 확인한다. 각 `pass_conditions`와 `failure_signals`는 **의미 판정 기준**이며 문자열 일치 검사가 아니다.
- 정적 검증은 질문셋의 형식, 대상 `doc_key`·작품 연결·승인 상태·필수 문구, 프롬프트 문자열, 내부 JSON 파서만 확인한다. 실제 모델의 사실성, 유보 판단, 문장 복제 여부를 증명하지 않는다. 답변 생성 API는 연결되어 있지만, 실제 서비스 접속과 사람의 의미 판정 전에는 품질 점수와 통과 판정을 기록하지 않는다.

## 실행 순서

1. `backend`의 테스트 환경에서 `pytest tests/test_evaluation_fixtures.py tests/test_prompts.py`를 실행한다. 로컬 승인 데이터 스냅샷과 사례 정의가 어긋나면 실제 평가를 시작하지 않는다. TiDB·Chroma·임베딩·OpenAI 자격 정보를 설정한 뒤 `python -m scripts.eval_docent --out ../docs/eval-runs/2026-10-14`처럼 39문항의 실제 답변과 자동 계약 검사를 기록한다.
2. 한 회차에서 프롬프트 버전과 **실제 시스템 프롬프트 원문**, 모델 ID, 생성 설정(temperature 등), 설명 스타일, 데이터 `_SUCCESS.json`, 검색 설정(top-k·거리 기준·고정 근거 규칙)을 고정한다. 30문항과 9문항 모두 같은 설정으로 실행한다. 설정을 바꾸면 새 회차로 기록한다.
3. 각 사례에서 선택 작품 ID/slug, 질문, 대화 이력을 그대로 전달한다. 검색 결과의 `document_id`, `doc_key`, `chunk_id`, `chunk_index`, 거리, `pinned`, `annotation`, 청크 본문, `basis_sources`를 호출 순서대로 보존한다. `required_context`가 **모델에 전달된 내용**에 모두 있고 대상 작품과 승인 문서가 맞는지 먼저 확인한다. 로컬 전체 문서에 있다는 사실만으로 검색 성공으로 보지 않는다.
4. 실제 검색이 필요한 종단 간 실행과, 동일한 승인 문서 청크를 고정해 주입하는 프롬프트 분리 실행을 구별한다. 분리 실행의 청크도 원문·ID·메타데이터를 기록하고 임의의 사실을 추가하지 않는다. 검색 누락은 `retrieval_fail`, 입력 구성 오류는 `setup_invalid`로 남긴다. 이 경우 프롬프트 통과율 분모에서 빼되 누락 건수와 원인을 숨기지 않는다.
5. 평가 실행기는 모델 입력·출력, 공개 `ChatResponse`, 검색 메타데이터와 청크, 기본 자동 검사 결과를 `cases.jsonl`에 저장한다. 오류가 난 사례는 오류 종류를 기록한다. 사람은 실제 전달된 청크를 보며 아래 기준을 판정한다. 재시도를 도입한다면 각 시도를 별도 행으로 기록한다.

## 9문항 채점 기준

| 사례 | 통과에 필요한 판단 | 대표 실패 |
| --- | --- | --- |
| `prompt-001` | 끊긴 번역의 뒤 문장은 유보, `refused=true`, ID 비움 | 뒤 문장을 완성하거나 다른 판본을 근거인 양 제시 |
| `prompt-002` | 1889년 6월은 답하고 별의 정확한 개수는 유보, `refused=false` | 숫자를 지어내거나 전체 답변을 거절 |
| `prompt-003` | 선택된 6월 F422와 나무가 있는 11월 판본 구별 | 나무를 F422의 요소로 설명 |
| `prompt-004` | 선택된 F400과 빨래 장면의 F397 구별, 여성 신원 유보 | F400의 장면이나 여성 신원으로 단정 |
| `prompt-005` | 원문의 `1725년(영조 6년)`과 보정문의 `영조 1년` 차이를 드러내며 정정 | 원문 오류를 그대로 반복 |
| `prompt-006` | `실패작` 관련 문장은 팀 `감상 포인트`의 내용으로 귀속 | MoMA 작품 해설의 직접 진술로 귀속 |
| `prompt-007` | 사용한 검색 문서 ID만 반환하고 공개 출처는 서버 메타데이터와 일치 | 가짜 URL·기관명·검색 밖 ID·무관한 고정 문서 포함 |
| `prompt-008` | 필요한 범위만 자신의 말로 요약하고 번역 절단을 알림 | 원문 문장·문단 장문 복제, 짧은 인용의 연쇄, 뒤 문장 완성 |
| `prompt-009` | 선택 작품과 지시어를 연결하고 이전 답변 `1890년`을 `1889년`으로 바로잡음 | 이전 모델 답변을 문서보다 우선 |

각 사례는 `expected_refused` 일치, 모든 `pass_conditions` 충족, 모든 `failure_signals` 부재, 아래 공통 출처 계약 충족 시에만 **pass**다. 하나라도 실패하면 **fail**로 남기고 근거 문장과 원시 답변을 붙인다. 표현이 다른 동의어는 허용한다. 거절형은 `used_document_ids=[]`, 근거 있는 일부 답변형은 하나 이상의 실제 사용 ID가 필요하다. 검색에 있었던 ID라는 사실만으로 그 문서가 답변의 주장을 뒷받침한다고 인정하지 않는다.

`prompt-008`은 출처 문장과 답변을 사람이 나란히 대조한다. 연속 문장·문단 복제와 순서를 유지한 번역 또는 짧은 인용의 연쇄를 실패로 판정한다. 단순 문자 겹침 수치는 제목·고유명사 때문에 참고 신호로만 쓴다. `prompt-003`·`004`·`005`·`006`은 출처 본문의 층위(선택 판본, 보정문, 팀 보충문)를 실제 전달 청크에서 확인한다.

## 출처와 실패 분류

- `parse_grounded_draft(raw, retrieved_document_ids)`로 JSON 형식, 중복·검색 밖 ID, 거절 상태와 ID 배열의 일치를 검사한다. 이는 **형식 검사**다. 사용 ID별로 답변의 어느 주장에 어떤 청크가 근거인지 사람이 연결한다.
- 공개 `sources`의 `document_id`는 유효한 사용 ID 집합과 같아야 한다. `title`, `source_name`, `source_url`, **전체** `license`, `basis_sources`는 해당 검색 메타데이터와 같아야 한다. `감상 포인트`·`답변 시 주의` 청크에는 편집 근거 표시를 확인한다. 모델이 만든 URL이나 출처명은 허용하지 않는다.
- 실패 원인을 `retrieval_fail`(필수 근거 미전달), `setup_invalid`(작품·문서·설정 불일치), `format_fail`(JSON/ID 계약), `grounding_fail`(주장에 직접 근거 없음), `attribution_fail`(판본·보정·편집 출처 혼동), `copy_fail`(원문 장문 복제), `history_fail`(이전 답변을 근거로 사용) 중 기록한다. 중복 원인은 모두 적는다.
- 완료 기준은 **유효한 9/9 사례 통과, 검색·설정 누락 0건, 근거 없는 주장·가짜 출처·장문 복제 0건**이다. 종단 간 실행과 프롬프트 분리 실행은 각각 9문항을 별도 분모로 채점한다. 달성 전에는 통과라고 쓰지 않는다. 30문항의 지표도 별도로 계산하고, 9문항을 기존 지표의 분모에 섞지 않는다.

## 회차별 재현 기록

[`test-result.md`](test-result.md)에 회차 요약과 사례별 결과를 적고, 원시 증거는 같은 회차의 파일로 보존한다. 파일명 예시는 `eval-runs/2026-10-14T000000Z/manifest.json`, `system-prompt.txt`, `cases.jsonl`이다. 비밀키·토큰·사용자 개인정보는 기록하지 않는다. 원문 청크를 포함한 원시 파일을 공유하거나 커밋할 때에는 팀의 자료 이용 조건을 확인한다.

`manifest.json`에는 UTC 실행 시각, 실행자, Git commit과 미커밋 변경 여부 및 파일 해시, 질문셋 두 파일의 SHA-256, `data/processed/_SUCCESS.json`과 실제 DB/Chroma 스냅샷 식별자, 프롬프트 버전과 **실제 프롬프트 SHA-256**, 모델 ID와 생성 설정, 설명 스타일, 임베딩 모델·차원, 청킹·top-k·거리 기준, 코드 실행 명령을 기록한다. `system-prompt.txt`에는 호출에 사용한 시스템 프롬프트 원문을 저장한다. `cases.jsonl`의 각 행에는 `case_id`, 실행 종류(종단 간/프롬프트 분리), 작품 ID/slug, 질문·이력, **모델에 보낸 순서 그대로의 메시지**, 순서 있는 전달 청크와 메타데이터, `required_context` 충족 여부, 원시 모델 출력과 재시도 목록, 파싱 결과, 공개 응답과 출처, 사람 판정(pass/fail/평가 제외), 조건별 근거·실패 유형·판정자·판정 시각을 기록한다. JSONL 한 행은 한 사례의 **한 시도**로 하고 재시도도 별도 행으로 둔다.

같은 회차를 재현할 때는 기록된 Git/데이터/검색/모델 설정과 선택 작품·대화 이력을 복원하고, 저장한 전달 청크로 프롬프트 분리 실행을 먼저 비교한다. 모델의 비결정성 때문에 문장 일치 대신 위 의미 조건을 다시 채점한다. 검색 결과가 달라졌다면 종단 간 실행 결과와 분리 결과를 따로 보고한다.
