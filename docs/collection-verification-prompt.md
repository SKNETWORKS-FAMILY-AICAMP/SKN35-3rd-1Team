## 사용자 요구사항 — 이 항목을 합격 기준으로 사용

### 1. 기존 감상 기록 기반 자동 모음

- 로그인 후 작품 상세를 열면 `POST /api/artworks/{id}/views`로 **그 로그인 사용자의** 조회 기록이 쌓여야 합니다.
- 컬렉션 탭에 ‘좋아요한 작품’ 기본 카드와 자동 모음이 표시되어야 합니다.
- `recent`: 상세 열람 작품 1점 이상, 최근 감상 순.
- `frequent`: 같은 작품 누적 조회 2회 이상. 같은 날 다시 열어도 횟수에 포함.
- `artist-{id}`: 같은 작가의 서로 다른 작품 2점 이상, 본 작품 수 기준 상위 작가 3명.
- `month-YYYY-MM`: 한국 시간 기준 이번 달에 본 작품 1점 이상.
- 빈 자동 모음은 카드로 표시하지 않습니다. 대표 이미지는 첫 작품 한 장입니다.
- 기존 recent/frequent/artist/month 모음은 일반 collections에 저장하지 않고 artwork_views에서 집계합니다.
- `/collection/auto/{key}`에서 상세 확인 후 ‘내 컬렉션으로 저장’할 수 있어야 합니다.
- 이번 제한 변경으로 각 감상 기록 자동 모음도 최대 30점을 반환하도록 수정했습니다.

### 2. 새 AI 취향 테마 모음 — 음악 앱의 개인 플레이리스트 같은 동작

- 단순 ‘모네 모음’이나 조회 날짜 묶음 외에, **실제 감상·좋아요 기록을 분석한 새로운 테마**를 만듭니다.
- 서로 다른 작품을 조회하거나 좋아요한 기록이 합쳐서 3점 이상이면 생성 대상입니다. 같은 작품의 조회·좋아요를 서로 다른 두 작품으로 세면 안 됩니다.
- 별도의 생성 버튼을 반드시 누르지 않아도 컬렉션 탭 진입 시 자동으로 준비합니다.
- 예: ‘고요한 산수와 자연의 숨결’, ‘빛이 머무는 풍경’ 등. 테마 이름을 고정 문자열로 넣은 가짜 AI 동작이면 안 됩니다.
- 모음은 **1~2개를 유지하고 갱신**하는 구조이며, 자동 테마가 계속 누적되는 구조는 아닙니다.
- 각 모음은 3~8점입니다. 실제 관심 작품을 최소 1점 포함하고, 테마가 맞는 미감상 작품도 섞을 수 있습니다.
- 후보에 여러 작가가 있으면 각 모음에 최소 두 작가를 포함합니다.
- 작품 ID는 실제 제공한 DB 후보 중에서만 선택하고 중복·존재하지 않는 ID·관심 작품이 전혀 없는 구성은 걸러야 합니다.
- 카드에 ‘AI 취향’ 배지와 선정 이유를 표시합니다. 이름뿐 아니라 작품 선정·순서에도 AI 결과가 반영되어야 합니다.
- 실제 좋아요·조회 근거 문장은 서버 기록으로 작성하고, AI의 미적 해석과 혼동하지 않아야 합니다.
- **기록/취향 신호가 같으면 기간 제한 없이 계속 유지**해야 합니다. 하루가 지났다는 이유만으로 재생성하면 안 됩니다.
- 기록/신호가 달라졌을 때 다음 컬렉션 탭 방문에서 갱신합니다. 과도한 호출 방지를 위한 최소 생성 간격은 30분입니다.
- 캐시는 재시작/다른 worker에서도 유지되는 사용자별 DB 스냅샷입니다. 한 사용자의 테마가 다른 사용자에게 노출되면 안 됩니다.
- AI 실패 또는 지연 때문에 일반 컬렉션과 기존 자동 카드를 숨기면 안 됩니다. 실패·준비 상태를 안내하고 기존 성공 결과는 보존해야 합니다.
- 테마 상세에서 일반 컬렉션으로 저장하면 구성은 별도로 보존됩니다. 자동 모음 갱신이 저장본을 바꾸면 안 됩니다.
- 데모 모드에서 가짜 테마를 실제 AI 결과처럼 표시하지 않습니다.

### 3. 직접 저장한 컬렉션 제한

- **계정당 최대 10개**, **컬렉션당 작품 최대 30점**입니다.
- 직접 생성, 작품 추가, 자동 모음 저장, AI 제안/MCP 경로에 같은 한도를 적용합니다.
- AI 모음을 직접 저장한 것도 10개에 포함합니다. 자동 AI 캐시 자체는 일반 저장 개수에 포함하지 않습니다.
- 10개까지 성공하고 11번째 새 컬렉션은 거부해야 합니다.
- 새 컬렉션에 30점을 한 번에 저장하는 것은 성공하고, 31점은 거부해야 합니다.
- 30점인 컬렉션에 새 작품 추가는 거부하되 이미 담긴 작품의 중복 추가는 멱등 성공해야 합니다.
- 삭제로 자리가 생기면 다시 추가할 수 있어야 합니다.
- 기존 한도 초과 데이터는 삭제·잘라내기·숨기기를 하지 않습니다. 조회/이름·소개 편집/삭제는 가능하고 새 추가만 막습니다.
- 데모 모드와 실제 API 모드가 일치해야 합니다.
- 한도 초과 오류를 ‘같은 이름이 있는지 확인’ 같은 다른 이유로 안내하면 안 됩니다.

### 4. 도슨트 제안과 실패 표시

- 로그인 회원이 같은 작품에 세 번째 이상 질문하고 현재 답변이 `refused=false`면 컬렉션 제안 대상입니다.
- 이미 저장한 작품 등 제외 규칙이 있으며, 같은 작가 작품 3점 이상을 봤고 같은 이름의 저장 모음이 없으면 작가 모음을 제안합니다.
- JSON 응답의 `suggestion`과 SSE 최종 `done` 프레임 양쪽에서 동작해야 합니다.
- 대화당 1회만 보여야 합니다. 화면 이탈·재진입, 새로고침, 대화 복원 시에도 요구사항과 맞는지 검증하세요.
- 제안만으로 저장하지 않고 사용자 수락 후 기존 저장 API를 호출합니다.
- 일반·감상 자동·AI 테마 요청의 로딩/실패를 분리합니다.
- 자동 API 오류를 `catchError => []`로 삼켜 ‘기록 없음’과 구분하지 못하는 문제가 재발하면 안 됩니다.
- 계정 전환/로그아웃/늦은 응답이 이전 계정의 데이터를 새 계정에 표시하면 안 됩니다.

## 특히 의심하고 확인할 부분

1. **요구와 구현의 차이**: 신호 지문은 최근 좋아요 30점·조회 30점으로 구성하고 조회 횟수를 3으로 제한합니다. 네 번째 이후 조회, 오래된 기록의 변화, 순서/재방문이 사용자 의도인 ‘기록 변경’에 맞게 반영되는지 판단하고 차이를 보고하세요.
2. **한도 경쟁 조건**: 단순 COUNT 검사 후 INSERT는 동시 요청으로 10개·30점 한도를 넘길 수 있습니다. 두 요청을 동시에 보내 실제 보장 여부를 검증하세요.
3. **대화당 한 번**: 프론트 메모리의 offered만으로 화면 복원까지 1회를 보장하는지, 서버가 반복 suggestion을 반환하는지도 확인하세요.
4. **AI 캐시 경합**: 첫 캐시 행 생성 경쟁, 원자적 attempted_at claim, worker 재시작/실패 후 재시도, 변경된 신호가 생성 중 도착하는 경우를 확인하세요.
5. **상세 안정성**: 목록에서 본 테마와 상세/저장할 작품 구성이 일치하는지, 갱신 시 theme-1/theme-2 링크가 기대대로 동작하는지 확인하세요.
6. **실제 모델 검증**: mock 성공만으로 완료 판정하지 마세요. 허용된 기존 서버 키로 제한된 실제 호출을 수행하고 테마의 근거·환각·선정 품질을 확인하세요. 키·토큰·비밀번호는 출력/파일 저장하지 마세요.
7. **실제 DB 방언**: SQLite 테스트와 TiDB/MySQL의 GROUP BY, 날짜/시간대, JSON, 캐시 UPDATE rowcount, 정렬·중복 키 동작을 구분하세요.
