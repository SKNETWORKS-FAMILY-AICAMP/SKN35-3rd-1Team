## A. 기획·서비스 가치

### 1. [최우선 / 1~4쪽] 도슨톡은 어떤 문제를 해결하는 서비스인가요?

**바로 말할 답변:** 미술 작품을 보면서 생기는 질문에 대해, 선택한 작품과 관련된 검수 자료를 찾아 출처와 함께 설명하는 AI 도슨트입니다. 감상 이후에는 열람 기록·감상평·컬렉션을 남겨 다음 감상으로 이어지도록 했습니다.

**상세 답변:** 일반적인 대화에서는 그럴듯한 설명이 나와도 제작 연도·소장처·인물 관계가 어디서 나온 정보인지 확인하기 어렵습니다. 저희는 답변의 유창함보다 근거의 범위와 추적 가능성에 초점을 맞췄습니다. 다만 “틀린 답을 절대 하지 않는다”는 뜻은 아니며, 검색·생성·출처·운영을 나눠 실패를 측정하고 제한하는 서비스입니다.

**꼬리질문:** 실제 고객의 필요를 확인했나요? → 현재 발표의 근거는 구현과 기술 평가입니다. 사용자 만족도나 학습 효과를 증명한 것은 아니며, 실제 관람객 사용성 검증은 다음 단계입니다.

### 2. [최우선 / 3~4쪽] 그냥 ChatGPT에 작품을 물어보면 되는데 차이가 뭔가요?

**바로 말할 답변:** 사용자가 직접 작품 정보와 자료를 매번 제공하지 않아도, 선택 작품의 승인 문서를 시스템이 제한해서 검색하고 근거 메타데이터를 붙인다는 차이가 있습니다.

**상세 답변:** 범용 모델과 지식량 경쟁을 하려는 것은 아닙니다. 작품 ID로 판본을 구별하고, 작품 해설·작가 생애·비교 문서·보정 내용을 연결하며, 사용한 문서 ID를 검증합니다. 또한 감상 기록과 개인 컬렉션이 같은 서비스에 이어집니다. 이 구조가 범용 챗봇보다 낫다는 사용자 비교 실험까지 한 것은 아니므로, 차별점은 기능·통제 구조로 설명하겠습니다.

### 3. [4쪽] 파인튜닝 대신 RAG를 선택한 이유는 무엇인가요?

**바로 말할 답변:** 바뀌는 작품 정보와 출처를 별도로 관리하고, 질문마다 어떤 자료를 근거로 썼는지 추적해야 했기 때문입니다.

**상세 답변:** 문서를 수정할 때 모델 가중치를 다시 학습하는 대신 데이터 적재·청킹·임베딩·검색 사본 동기화로 반영합니다. 또 작품별 검색 범위를 DB 관계로 제한할 수 있습니다. 파인튜닝은 답변 스타일 등 다른 목적에 사용할 수 있지만, 현재 규모와 요구에서는 출처를 가진 검색 체계가 우선이었습니다. 두 방식을 동일 조건으로 비교한 실험은 없으므로 RAG가 모든 경우에 우월하다고 말하지는 않겠습니다.

### 4. [2·5쪽] 작품과 작가를 제한한 이유는 무엇인가요? 너무 적지 않나요?

**바로 말할 답변:** 넓게 답하는 것보다 수집·검수·출처 연결까지 확인할 수 있는 범위를 먼저 완성하려고 작가 10명으로 시작했습니다.

**상세 답변:** 서양 8명과 조선 2명, 작품 277점에 대해 작품 해설뿐 아니라 생애·연표·비교 문서를 연결했습니다. 범위가 작다는 것은 서비스의 한계입니다. 확장 시에는 숫자만 늘리기보다 별칭·작품 식별·자료 권리·승인 상태·정답셋을 함께 추가해야 합니다. 현재 데이터가 미술 전체를 대표한다고 보지는 않습니다.

### 5. [5쪽] 왜 직접 모으고 검수했나요? 인터넷 검색을 붙이면 더 편하지 않나요?

**바로 말할 답변:** 질문마다 다른 웹 문서를 가져오면 자료의 품질과 이용 조건이 바뀌고, 결과를 같은 기준으로 재검증하기 어려워서입니다.

**상세 답변:** 저희는 원본·정제 산출물·승인 기록을 분리하고, 문서 키와 출처를 유지했습니다. 이를 통해 오류를 발견했을 때 원문 문제인지 검색 문제인지 추적할 수 있습니다. 실시간 웹 검색은 최신 정보를 얻는 장점이 있지만, 현재 서비스는 검수한 고정 자료를 우선하는 설계를 선택했습니다.

### 6. [2·9쪽] 도슨트와 서재·감상평·컬렉션은 왜 한 서비스에 넣었나요?

**바로 말할 답변:** 질문에 답한 뒤 감상이 끝나는 대신, 사용자가 본 작품을 기록하고 다시 탐색하도록 연결하려고 넣었습니다.

**상세 답변:** 열람 기록은 캘린더와 자동 컬렉션의 근거가 되고, 좋아요는 개인 추천의 주요 신호가 됩니다. 공개 감상평은 피드와 감상가 프로필에, 비공개 감상은 개인 기록에 남습니다. 다만 체류 시간이나 재방문율이 좋아졌다는 지표는 아직 없으므로 제품 설계 의도와 검증된 사용자 효과를 구분합니다.

### 7. [9·12쪽] Easy·Standard·Deep은 답변 길이만 바꾸는 건가요?

**바로 말할 답변:** 기본 분량뿐 아니라 용어 수준, 근거를 연결하는 방식, 배경 설명의 깊이를 구분합니다.

**상세 답변:** Easy는 일상어와 핵심 근거를, Standard는 표현 방식과 효과의 연결을, Deep은 관련 근거가 충분할 때 기법과 시대·작가 맥락을 더 깊게 연결합니다. 세 스타일 모두 같은 근거 제한을 받습니다. 단일 사실 질문에는 Deep이어도 짧게 답할 수 있고, 근거가 부족하면 분량을 채우기 위해 내용을 만들지 않습니다.

### 8. [7·9쪽] 왜 Flutter Web과 FastAPI를 선택했나요?

**바로 말할 답변:** 프론트는 작품 탐색과 채팅·서재 화면을 하나의 UI로 구성하고, 백엔드는 Python의 검색·LLM·DB 라이브러리를 연결하기 위해 선택했습니다.

**상세 답변:** Flutter 화면과 FastAPI는 HTTP API 계약으로 분리되어 있고, 백엔드는 Pydantic 스키마로 입출력을 정의합니다. FastAPI에서는 JSON 응답과 SSE를 제공하고 LangChain·SQLAlchemy와 연결합니다. 이 조합이 React 등 다른 선택보다 빠르다는 성능 비교는 하지 않았으므로, 팀의 구현 환경과 Python 생태계 적합성으로 설명하는 것이 정확합니다.

## B. 데이터·출처·검수

### 9. [최우선 / 5~6쪽] “검수 완료”는 무엇을 확인했다는 뜻인가요?

**바로 말할 답변:** 자료의 출처·작품 연결·본문과 보충 설명 등을 팀 기준으로 검토했고, 전처리 결과에서 검수 대기 표시가 남은 문서는 없다는 뜻입니다.

**상세 답변:** 현재 산출물의 needs_review 문서는 0건입니다. 그러나 이는 미술사 전문가의 독립 검증이나 사실 오류 0건을 뜻하지 않습니다. 검수 상태·원문·승인 이력을 남겨 다시 확인할 수 있도록 했고, 자료 자체의 오류 가능성은 보정문과 재검수로 관리합니다.

**꼬리질문:** 작성자와 검수자가 같으면 객관적인가요? → 독립 검수의 강도가 제한된다는 점을 인정하고, 기관별 원문 대조와 외부 전문가 검토를 보강해야 합니다.

### 10. [6쪽] 문서는 어디서 모았고 신뢰도는 어떻게 다뤘나요?

**바로 말할 답변:** 발표 자료 기준으로 위키백과, 해외 미술관, 국립중앙박물관, 한국민족문화대백과사전 등의 자료를 사용했고 문서별 출처 URL과 이용 조건을 남겼습니다.

**상세 답변:** 기관 이름 하나로 모든 문장을 같은 수준으로 신뢰하지는 않습니다. 특정 작품의 연도·소장처는 그 작품을 직접 식별하는 기관 기록을 우선 확인하고, 일반 배경·팀 해석을 구분합니다. 충돌을 해소할 근거가 부족하면 차이를 밝히고 유보하는 것이 답변 원칙입니다.

### 11. [최우선 / 6쪽] 출처와 라이선스를 적었으면 자유롭게 사용할 수 있는 건가요?

**바로 말할 답변:** 출처를 적었다는 사실과 재사용 권한은 구분합니다. 문서 본문·팀 작성 해설·작품 이미지의 이용 조건도 각각 다르게 관리합니다.

**상세 답변:** 저장소에서는 원문 링크와 라이선스, 이미지 출처를 따로 유지하고, 팀 해설은 참고 기관의 공식 문장인 것처럼 표시하지 않습니다. 권리 검토로 배포에서 제외한 작품 기록도 있습니다. “모든 자료의 모든 이용이 허가됐다”는 식으로 확대해 말하지 않고, 발표 수치는 현재 데이터의 관리·분류 기록이라고 설명하겠습니다. 이 답변은 프로젝트 처리 방식 설명이며 외부 기관의 최신 이용 조건 전체를 검증했다는 뜻은 아닙니다.

### 12. [5~6쪽] 번역·전처리 과정에서 의미가 바뀌거나 데이터가 손상되지 않나요?

**바로 말할 답변:** 그 가능성을 줄이기 위해 원본을 보존하고, 정제·번역 산출물과 출처·해시 기록을 분리했습니다.

**상세 답변:** 원본 형식이 JSON·Markdown·연표로 달라도 적재용 JSONL로 통일하고, slug와 doc_key로 작품·문서 연결을 확인합니다. 원문과 번역본은 같은 주제일 수 있으므로 검색 자리와 평가에서 중복을 고려합니다. 하지만 구조 검증이 번역의 의미 정확성까지 보장하지 않아서, 끊긴 번역을 임의로 완성하지 않는 사례도 별도로 평가했습니다.

### 13. [8·12쪽] “감상 포인트”와 “답변 시 주의”는 무엇이 다른가요?

**바로 말할 답변:** 감상 포인트는 팀이 덧붙인 관람·해석 제안이고, 답변 시 주의는 알려진 오류나 오해를 바로잡기 위한 보정 정보입니다.

**상세 답변:** 두 절은 원문 본문과 별도 청크로 만들고 annotation과 basis_sources를 전달합니다. 답변 시 주의는 충돌하는 원문 설명을 정정할 때 우선 참고하고, 감상 포인트는 기관이 직접 주장한 사실처럼 귀속하지 않도록 합니다. 둘 다 아무 근거 없는 팀 의견을 자동으로 사실화하는 장치는 아닙니다.

### 14. [4·10쪽] 문서를 고치면 정말 바로 답변에 반영되나요?

**바로 말할 답변:** 모델 재학습 없이 반영할 수 있다는 뜻이며, 파일을 저장하는 즉시 자동 반영되는 구조는 아닙니다.

**상세 답변:** 원본·매핑 수정 후 전처리, TiDB 문서 적재, 변경 청크 생성·임베딩, Chroma 동기화가 필요합니다. 문서 메타데이터만 바뀐 경우와 검색 벡터까지 바뀌는 경우도 다릅니다. 반영 후 같은 질문으로 검색·답변을 재검증해야 합니다. 슬라이드의 “바로 반영”은 “적재·동기화 후 재학습 없이 반영”으로 설명하겠습니다.

## C. RAG·검색·벡터 DB

### 15. [최우선 / 7~8쪽] 질문 하나가 들어오면 정확히 어떤 순서로 처리되나요?

**바로 말할 답변:** 작품을 확인하고 질문을 분류한 뒤, 관련 문서만 검색해 모델에 전달하고, 반환한 문서 ID를 검증해 최종 출처를 조립합니다.

**상세 답변:** 규칙 분류에서는 범위 밖 작가·잡담·추천 요청 등을 구분합니다. 필요한 경우 별도 의미 범위 판정도 사용합니다. RAG 경로에서는 SQL로 승인 문서 범위를 제한하고 질문 임베딩으로 Chroma를 검색합니다. 생성 모델에는 선택 작품·질문·필요한 이력·검색 근거를 전달합니다. 로그인 대화는 최종 답변 검증 후 저장하며, 작가 이름 같은 단순 질문이나 추천은 일반 RAG 생성 경로를 생략할 수 있습니다.

### 16. [최우선 / 7·10쪽] TiDB도 벡터 검색을 지원하는데 Chroma까지 쓰는 이유는요?

**바로 말할 답변:** 관계·문서·벡터의 기준 저장소를 TiDB에 두고, RAG 검색용 사본을 Chroma에 두는 역할 분리를 선택했습니다.

**상세 답변:** TiDB는 작품·작가·문서 연결과 사용자 활동을 SQL로 관리하고 벡터 원본도 보관합니다. Chroma는 범위 안 청크 검색을 담당합니다. 덕분에 검색 사본이 사라져도 저장된 벡터를 복사해 복원할 수 있습니다. 대신 동기화·운영 복잡성이 늘어납니다. 현재 규모에서 두 DB가 필수라는 뜻도, Chroma가 TiDB보다 빠르다는 비교 실험을 마쳤다는 뜻도 아닙니다.

### 17. [최우선 / 10쪽] 두 저장소가 어긋나면 어떻게 하나요?

**바로 말할 답변:** TiDB를 기준으로 삼고 동기화 스크립트가 Chroma에 필요한 청크를 추가하고 사라진 청크를 제거합니다.

**상세 답변:** Chroma ID를 TiDB 청크 ID와 연결하고, 컬렉션의 모델 이름·거리 함수도 검사합니다. 다만 두 저장소를 묶은 원자적 트랜잭션은 없으므로 문서 수정·동기화 사이에 불일치할 수 있습니다. 운영 확장 시에는 버전별 컬렉션을 만든 뒤 전환하거나 동기화 상태를 검증하는 배포 절차가 필요합니다. “실시간 강한 일관성”을 구현했다고 말하지는 않습니다.

### 18. [10쪽] Chroma 유실 시 10초·비용 0원이라는 건 어떤 의미인가요?

**바로 말할 답변:** 기존 실험 규모에서 TiDB에 저장된 벡터를 재사용해 복원했으며, OpenAI 재임베딩 호출이 없다는 뜻입니다.

**상세 답변:** 10초는 해당 데이터·네트워크·실행 환경에서의 관찰값으로 모든 규모의 복구 시간 보장이 아닙니다. 비용 0원도 “재임베딩 API 비용이 추가되지 않는다”는 의미입니다. DB·네트워크·실행 인프라 비용까지 모두 없다는 뜻은 아니고, 최신 427문서의 현재 복원 시간을 별도 측정 없이 동일하다고 말하지 않습니다.

### 19. [10쪽] text-embedding-3-small과 1536차원은 왜 선택했나요?

**바로 말할 답변:** 현재 문서·질문을 같은 임베딩 공간에 놓고, 1536차원으로 DB 스키마와 검색 사본을 일치시키는 구성을 사용했습니다.

**상세 답변:** 모델은 설정으로 관리하고 결과 차원을 코드에서 검사합니다. 다른 모델보다 최선이라는 비교 실험은 없어서 “검증된 최적 모델”이라고 하지는 않습니다. 모델을 바꾸면 같은 차원이어도 벡터 의미 공간이 달라질 수 있어 청크·작품 벡터와 Chroma를 함께 재생성해야 하고, 차원까지 바뀌면 DB 마이그레이션도 필요합니다.

### 20. [10·15쪽] 문서는 어떤 크기로 잘랐나요? 왜 그 크기인가요?

**바로 말할 답변:** 일괄 고정 길이 대신 문서 구조를 살렸습니다. 짧은 본문은 통째로 유지하고 긴 문서는 제목·문단·문장 경계로 나눴습니다.

**상세 답변:** 코드 기준 본문 1,200자 이하는 보존하고, 긴 섹션은 목표 500자·하드 기준 800자, 작은 조각은 150자 기준으로 병합합니다. 감상 포인트·답변 시 주의는 본문과 분리합니다. 숫자는 문자 기준이고 모델 토큰 수와 같지 않습니다. 작은 조각의 맥락 손실과 큰 조각의 검색 정밀도 저하 사이에서 도메인 문서에 맞춰 선택한 규칙이며, 모든 데이터에 최적인 값은 아닙니다.

### 21. [최우선 / 15쪽] overlap이 보통 좋다는데 왜 0자를 썼나요?

**바로 말할 답변:** 저희 자료에서는 기존 청크에 이전 청크 끝 0·50·100자를 붙인 비교 실험에서, overlap을 늘려도 주요 검색 지표가 좋아지지 않았기 때문입니다.

**상세 답변:** 0자 Recall@5는 0.7870, 50자는 0.7685, 100자는 0.7500이었습니다. 다만 nDCG@5는 100자에서 0.7563으로 0자의 0.7514보다 조금 높았습니다. 따라서 “모든 지표에서 0자가 최고”가 아니라 “이번 18문항 실험에서 overlap 증가의 일관된 개선이 없어 기본값을 유지했다”가 정확합니다. 완전히 다른 경계로 다시 청킹한 모든 방식을 비교한 실험도 아닙니다.

### 22. [최우선 / 8·15쪽] 검색 대상 문서를 어떻게 제한하나요?

**바로 말할 답변:** 질문과 비슷한 문서를 전부 검색하기 전에, 선택 작품과 작가에 연결된 승인 문서 ID를 SQL로 정합니다.

**상세 답변:** 작품 자신의 해설, 해당 작가의 생애·연표, 관련 비교 문서를 관계 테이블로 연결하고 needs_review 문서는 제외합니다. 이 ID 집합을 Chroma 필터에 적용합니다. 목적은 다른 작품이나 작가의 설명이 우연히 비슷하다는 이유로 섞이는 것을 줄이는 것입니다. 범위가 좁아서 놓치는 비교 질문은 있을 수 있으며, 실제 비교 근거가 없으면 일반지식으로 채우지 않습니다.

### 23. [최우선 / 15쪽] 보장 자리·고정 근거는 정답을 미리 넣어 주는 것 아닌가요?

**바로 말할 답변:** 특정 질문의 정답 문장을 넣는 대신, 선택 작품 해설·비교 문서·작품에 연결된 연표처럼 일반화된 관계 규칙으로 검색 누락을 줄인 것입니다.

**상세 답변:** 일반 검색에 작품 해설 최대 3개, 비교 질문에는 비교 문서 최대 2개를 추가하고, 연표·보정 근거를 붙입니다. 긴 생애 문서가 상위를 독점하지 않도록 일반 순위에서는 문서별 상한도 둡니다. 다만 같은 평가셋을 보고 개선했으므로 평가셋에 대한 튜닝 편향 가능성은 있습니다. 보정 없는 결과와 분리해 공개하고, 보지 않은 질문으로 추가 검증하는 것이 필요합니다.

### 24. [최우선 / 13·15쪽] 문서 Hit@5 100%인데 청크 지표는 왜 낮나요?

**바로 말할 답변:** 평가 단위와 검색 방식이 다릅니다. 문서 평가는 규칙 보강까지 포함한 최종 검색 결과이고, raw 청크 평가는 별도 18문항에서 순수 코사인 상위 5개를 봅니다.

**상세 답변:** 정답 문서가 결과에 있어도 그 문서의 필요한 문단이 상위에 없을 수 있습니다. 더 중요한 점은 문서 평가 스크립트가 최종 반환 전체를 확인하므로, 슬라이드의 “문서 Hit@5”는 엄밀한 순수 top-5 지표가 아닙니다. 실제 targeted 질문의 반환 청크는 5~11개였습니다. 발표에서는 “최종 검색 근거 문서 적중률 23/23”으로 고쳐 말하고 raw 청크 Hit@5와 구분하는 것이 정확합니다.

### 25. [16쪽] 코사인 거리가 가까우면 답할 수 있다고 보면 안 되나요?

**바로 말할 답변:** 가까운 문장은 질문과 의미상 비슷할 수 있지만, 질문의 특정 사실을 직접 뒷받침한다는 보장은 없기 때문입니다.

**상세 답변:** 평가에서도 답할 질문과 거절할 질문의 최상위 거리 범위가 겹쳤습니다. 하나의 임계값으로 자르면 정상 질문을 거절하거나 범위 밖 질문을 통과시킬 수 있습니다. 따라서 거리는 검색 순위에 사용하고, 작가·작품 범위 분류와 근거 유무 판단·출력 검증을 별도로 적용했습니다. 다른 데이터에서 거리 임계값이 항상 무의미하다는 주장까지 하는 것은 아닙니다.

### 26. [15·21쪽] 검색을 더 개선한다면 무엇부터 하겠습니까?

**바로 말할 답변:** 실패한 질문에서 정답 라벨·작품 식별·청크 맥락을 먼저 확인하고, 그다음 키워드와 벡터를 결합하는 검색을 비교하겠습니다.

**상세 답변:** 작품명·연도·판본 번호처럼 정확한 문자열이 중요한 질문은 의미 벡터만으로 놓칠 수 있습니다. BM25 같은 키워드 검색이나 reranker는 후보 개선 방향이지만 현재 구현 완료 기능은 아닙니다. 각각 추가한 뒤 동일한 미사용 평가셋으로 raw 검색과 최종 답변 품질·지연을 함께 비교해야 합니다.

## D. 생성·출처·환각·스트리밍

### 27. [최우선 / 1·12·17쪽] “근거 안에서만 말한다”면 환각을 완전히 막았다는 뜻인가요?

**바로 말할 답변:** 완전한 보장이라기보다 시스템의 목표와 제약입니다. 승인 범위 검색·질문 분류·프롬프트·출처 ID 검증을 여러 단계에 적용했습니다.

**상세 답변:** 검색 문서가 맞아도 모델이 잘못 해석하거나 출처에 없는 주장을 덧붙일 가능성은 남아 있습니다. 최종 검증은 문서 ID와 형식·URL 등의 계약을 검사하고, 모든 문장의 의미를 독립적으로 증명하는 것은 아닙니다. 이번 평가에서는 거절 필요 8건에서 명확한 환각을 관찰하지 않았지만, 임의의 모든 질문에서 환각 0%라는 뜻은 아닙니다.

### 28. [11쪽] LangChain은 정확히 어디에 사용했나요? 없어도 구현할 수 있지 않나요?

**바로 말할 답변:** 검색 결과를 Document로 통일하고, ChatOpenAI의 구조화 출력과 스트리밍 파서를 연결하는 데 사용했습니다.

**상세 답변:** 검색 담당과 생성 담당이 page_content와 metadata를 주고받는 계약을 맞추는 데 도움이 됐습니다. JSON 경로에서는 with_structured_output으로 답변·거절·사용 문서 ID를 받고, SSE에서는 증분 JSON 파싱 후 같은 최종 검증을 적용합니다. 직접 SDK로도 만들 수 있는 구조이며, LangChain 자체가 답변의 사실성을 보장하는 것은 아닙니다.

### 29. [11쪽] 구조화 출력이면 틀린 답을 막을 수 있나요?

**바로 말할 답변:** 구조화 출력은 검증 가능한 형식을 만드는 수단이고, 내용이 참임을 보장하는 수단은 아닙니다.

**상세 답변:** answer·refused·used_document_ids를 받아 정수 ID·중복·검색 결과 포함 여부·거절 상태와 ID 배열의 일치 등을 검사합니다. 예를 들어 거절인데 출처 ID가 있거나 사실 답변인데 출처 ID가 없으면 거부합니다. 그러나 유효한 ID를 붙이고 그 문서와 다른 주장을 하는 오류는 별도 의미 평가가 필요합니다.

### 30. [최우선 / 17쪽] 출처는 정말 서버가 만드나요? LLM이 만든 출처는 안 섞이나요?

**바로 말할 답변:** 모델은 사용했다고 판단한 문서 ID만 반환하고, 제목·원문 URL·라이선스·편집 근거는 서버가 검색 메타데이터에서 조립합니다.

**상세 답변:** 검색 결과 밖의 ID나 중복 ID는 검증에서 거절하고, 답변 본문에 임의의 URL이 있으면 차단합니다. 따라서 모델이 가짜 기관 링크를 만들어 출처로 내보내는 경로를 줄였습니다. 다만 “실제로 사용했다”는 모델의 자기 보고와 “그 문서가 모든 주장을 지지한다”는 것은 다르므로 문장 단위 의미 정합은 추가 검증 대상입니다.

### 31. [12쪽] 문서나 질문에 “규칙을 무시하라”고 쓰면 어떻게 되나요?

**바로 말할 답변:** 문서·과거 답변 속 지시는 데이터로 취급하도록 시스템 규칙을 두고, 도슨트가 실행할 수 있는 작업도 제한합니다.

**상세 답변:** 답변에는 임의의 링크를 만들지 못하게 하고, 출처는 서버가 확인한 ID로만 구성합니다. 컬렉션 변경도 도슨트 본문 생성이 직접 수행하지 않습니다. 다만 프롬프트 규칙만으로 모든 공격을 막는다는 보장은 없으므로 여러 공격형 문서·멀티턴 입력을 추가한 회귀 평가가 필요합니다. 현재 공개한 기능 검증과 포괄적인 보안 검증은 구분합니다.

### 32. [9·12쪽] 이 모델은 작품 이미지를 직접 보나요? 색이나 인물 수를 어떻게 설명하나요?

**바로 말할 답변:** 현재는 이미지 자체를 분석하는 멀티모달 도슨트가 아니라, 작품에 관한 문서를 검색하는 텍스트 RAG입니다.

**상세 답변:** 문서에 색·구도·인물 설명이 있으면 그 범위에서 답하고, 직접 그림을 관찰한 것처럼 말하지 않도록 했습니다. 별의 정확한 수나 인물의 신원처럼 문서에 없는 세부는 유보합니다. 향후 이미지 분석을 넣어도 관찰 결과와 문헌 해석을 구분하고, 판본·오인식 문제를 별도로 평가해야 합니다.

### 33. [9·12쪽] “그 사람은?” 같은 후속 질문을 어떻게 이해하나요?

**바로 말할 답변:** 최근 대화를 답변 맥락으로 전달하고, 지시어가 있는 검색 질문에는 최근 사용자 질문을 함께 붙입니다.

**상세 답변:** 과거 모델 답변을 새로운 사실 근거로 사용하면 이전 오류가 이어질 수 있어서 검색어 보강에는 이전 사용자 질문을 사용합니다. API는 history 최대 12개를 받고, 현재 생성용 context는 최근 6개를 각 600자까지 전달합니다. 따라서 슬라이드의 “최근 12개 전달”은 API 수신 한도와 실제 생성 입력을 구분해야 합니다. 의미가 불명확하면 짧게 되묻는 경로도 있습니다.

### 34. [최우선 / 18쪽] SSE로 보여 주면 검증 전 틀린 문장이 먼저 나가지 않나요?

**바로 말할 답변:** 현재 구조에서는 생성 중 텍스트가 먼저 보일 수 있습니다. 검증된 최종 결과는 done 이벤트이고, 검증 후 내용이 바뀌면 replace로 전체를 교체합니다.

**상세 답변:** 이 방식은 체감 대기 시간을 줄이지만 중간 문장 노출 위험을 없애지는 못합니다. 그래서 “사용자에게 보이는 모든 글자가 사전 검증됐다”고 말하면 안 됩니다. 더 강한 검증이 필요하면 전체 답변을 버퍼링한 뒤 내보내거나 문장 단위 검증을 붙일 수 있지만, 첫 표시 지연과 추가 비용을 함께 비교해야 합니다.

### 35. [최우선 / 17·19·21쪽] 답변은 안전한데 refused=false인 두 건을 왜 실패로 봤나요?

**바로 말할 답변:** 본문은 “확인할 수 없다”고 했지만 API 상태값은 답변 가능으로 표시해서, 내용과 계약이 서로 달랐기 때문입니다.

**상세 답변:** 한 건은 고흐가 그림을 그리던 순간의 심리 상태를 하나로 단정하라는 요청이고, 다른 한 건은 끊긴 묵서 문장을 완성하라는 요청입니다. 둘 다 사실을 지어내지 않았지만 핵심 요청을 수행하지 못했는데 refused=false가 반환됐습니다. UI·집계·후속 동작이 이 값을 사용할 수 있으므로 계약 실패로 처리했습니다. 안전한 내용 8/8과 상태값 6/8을 따로 보고하는 이유입니다.

### 36. [12·17쪽] 일부만 답할 수 있을 때와 아예 모를 때는 어떻게 구분하나요?

**바로 말할 답변:** 핵심 질문에 근거가 전혀 없으면 거절하고, 확인된 부분을 실제로 설명할 수 있으면 그 부분은 답하면서 나머지를 유보합니다.

**상세 답변:** 예를 들어 제작 시기는 자료로 답할 수 있지만 화면 속 별 개수는 알 수 없을 때는 제작 시기를 설명하고 개수는 확인할 수 없다고 말할 수 있습니다. 이때는 근거 있는 일부 답변으로 refused=false가 가능합니다. 반면 질문의 핵심을 답하지 못했는데 주변 사실만 붙여 false로 만드는 것은 막아야 합니다. 현재 두 잔존 오류가 바로 이 의미 경계의 문제입니다.

## E. 평가·수치·실험 설계

### 37. [최우선 / 13~19쪽] 종합 95.6%는 무엇을 나눈 값인가요?

**바로 말할 답변:** 6회차 배포 API의 고정 45문항 중 평가 기록에서 통과로 판정한 43문항을 나눈 값입니다.

**상세 답변:** 질문은 회귀 30개·정확도 집중 9개·말투 및 청크 경계 보충 6개입니다. HTTP 성공률 45/45와 다르고, LLM Judge 점수 평균과도 다른 지표입니다. 이 수치를 서비스 전체 정확도나 모든 미술 질문의 정답률이라고 부르지 않습니다. 두 실패의 상태값 불일치도 분모에서 빼지 않고 포함했습니다.

### 38. [최우선 / 14쪽] 45문항으로 성능을 주장하기에는 너무 적지 않나요?

**바로 말할 답변:** 전체 사용자 질문을 대표하기에는 작습니다. 현재는 기능별 오류를 재현하고 수정 여부를 확인하는 회귀 평가로 해석하고 있습니다.

**상세 답변:** 사실·해석·비교·범위 밖·자료 부족·멀티턴 등 유형을 나눴지만, 질문 표현·작가·판본·긴 대화의 다양성은 충분하지 않습니다. 같은 셋을 반복 사용해 튜닝했으므로 미사용 질문 평가가 필요합니다. 새 작가·다른 표현·공격형 질문·불확실한 근거를 포함한 별도 테스트와 반복 실행으로 일반화 가능성을 확인하겠습니다.

### 39. [13~16쪽] Hit·Recall·MRR·nDCG는 각각 무엇을 보나요?

**바로 말할 답변:** Hit은 하나라도 찾았는지, Recall은 필요한 정답을 얼마나 찾았는지, MRR은 첫 정답이 얼마나 앞에 있는지, nDCG는 정답들이 앞쪽에 잘 배치됐는지를 봅니다.

**상세 답변:** 정답 청크가 2개인데 5개 결과 중 하나만 있으면 Hit@5는 1, Recall@5는 0.5입니다. 첫 정답이 2위면 reciprocal rank는 1/2이고, MRR은 이를 문항별로 평균한 값입니다. 현재 nDCG는 정답 청크 여부를 이진 관련성으로 계산합니다. 지표를 함께 보면 문서를 찾았어도 필요한 두 문단 중 하나가 빠졌는지 확인할 수 있습니다.

### 40. [최우선 / 14·16쪽] RAGAS를 썼다는 건 공식 라이브러리를 실행했다는 뜻인가요?

**바로 말할 답변:** 이 평가에서는 RAGAS의 지표 정의를 참고한 고정 프롬프트와 구조화 LLM Judge를 사용했습니다. 공식 라이브러리의 전체 절차를 그대로 실행한 결과라고 표현하면 부정확합니다.

**상세 답변:** Judge에 질문·답변·기대 조건·검색 context를 주고 faithfulness·relevancy·correctness를 0~1로 받습니다. 구현과 프롬프트를 저장해 반복 실행할 수 있도록 했지만, 다른 구현의 RAGAS 점수와 직접 등가라고 볼 수는 없습니다. 발표에서는 “RAGAS 기준을 참고한 LLM Judge 평가”라는 표현을 사용하겠습니다.

### 41. [최우선 / 16쪽] 답변한 모델과 채점한 모델이 같으면 자기 편향 아닌가요?

**바로 말할 답변:** 그 가능성이 있습니다. 실제로 평가 코드는 설정된 assistant_model을 Judge에도 쓰므로 독립적인 정답 판정이라고 보기는 어렵습니다.

**상세 답변:** 고정 프롬프트와 구조화 출력으로 기준을 일정하게 했지만 같은 모델 계열의 판단 습관과 표현 선호가 반영될 수 있습니다. 1.00도 객관적 완벽함을 뜻하지 않습니다. 개선 시에는 다른 모델 Judge, 블라인드 사람 평가, 미사용 질문셋을 함께 적용하고 서로 다른 판정이 나는 사례를 재검토하겠습니다.

### 42. [최우선 / 16쪽] Answer Correctness 1.00인데 왜 종합은 95.6%인가요?

**바로 말할 답변:** 분모와 채점 기준이 다르기 때문입니다. 생성 Judge 평균은 정상 답변 기대 37문항이고, 종합 통과는 거절 기대를 포함한 45문항입니다.

**상세 답변:** 남은 두 실패는 거절 기대 사례의 refused 계약 불일치여서 생성 평균 37문항에 포함되지 않습니다. 또 Judge의 1.00은 제공한 context·expected와 그 채점 방식에서의 결과이며 미술 지식 전체의 사실 정확도 100%가 아닙니다. 서로 다른 모집단과 평가 방법의 수치를 하나로 해석하지 않는 것이 중요합니다.

### 43. [14·16쪽] Judge는 실제 생성에 사용한 근거를 그대로 보고 평가했나요?

**바로 말할 답변:** 현재 eval_round3 구현은 API 답변을 받은 뒤 로컬 retriever로 context를 다시 검색해서 Judge에 전달합니다. 생성 시점 입력을 완전히 그대로 캡처한 구조는 아닙니다.

**상세 답변:** 따라서 운영 생성의 실제 청크와 사후 재검색 청크가 항상 동일하다고 보장할 수 없습니다. 후속 질문의 검색어 구성이나 데이터 변경이 있으면 더 차이가 날 수 있습니다. 이 점은 현재 faithfulness 평가의 한계입니다. 개선 시에는 요청별 검색 결과·프롬프트 버전·실제 전달 메시지를 trace로 남기고 그 입력으로 채점해야 합니다.

### 44. [최우선 / 19쪽] 회차마다 문항 수가 다른데 86.7%에서 95.6%로 좋아졌다고 해도 되나요?

**바로 말할 답변:** 회차별 관찰 결과로는 제시할 수 있지만, 문항 구성이 다른 회차를 같은 모집단의 정밀한 개선율처럼 직접 비교하면 안 됩니다.

**상세 답변:** 2회차는 30문항, 3회차부터는 45문항입니다. 따라서 2차와 3차 이후 비율은 분모·구성 차이를 함께 밝혀야 합니다. 같은 45문항을 쓴 후기 회차의 개선과 같은 조건의 개별 실패 해결을 중심으로 설명하고, 전체 추세는 평가 이력으로 제시하겠습니다. 모델 비결정성도 있어 단일 실행 변화 전부를 코드 효과로 단정할 수는 없습니다.

### 45. [17쪽] 출처 정합 100%면 답변의 모든 문장이 검증됐다는 뜻인가요?

**바로 말할 답변:** 아닙니다. 출처 ID·기대 문서·메타데이터 계약이 맞는 것과, 모든 사실 문장이 그 출처로 직접 입증되는 것은 다릅니다.

**상세 답변:** 현재 출처 검사는 잘못된 문서 ID나 가짜 URL을 막는 데 의미가 있습니다. 그러나 여러 사실이 들어간 답변의 각 문장을 어떤 근거가 지지하는지까지 완전히 자동 증명하지는 않습니다. 더 강하게 검증하려면 주장 단위 근거 매핑과 독립적인 의미 판정을 추가해야 합니다. “출처 정합”의 정의를 좁고 정확하게 설명하겠습니다.

### 46. [17쪽] 출처 링크 37/38은 왜 100%가 아닌가요?

**바로 말할 답변:** 한 링크는 자동 요청과 보조 확인 모두 접근이 제한되어 존재·내용을 자동 확인하지 못했습니다.

**상세 답변:** 일부 403 페이지는 보조 웹에서 페이지 존재를 확인했고, Belvedere 한 페이지는 확인 불가로 남겼습니다. 그래서 37개 확인을 모두 “직접 GET 200”이라고 말하면 안 됩니다. 접근 제한과 링크 삭제는 다르므로 확인 불가를 곧바로 잘못된 출처라고 단정하지 않고 수동 확인 대상으로 둡니다.

### 47. [18쪽] P95 5.9초면 느린 것 아닌가요? SSE는 몇 초에 시작하나요?

**바로 말할 답변:** 이번 평가의 JSON 응답 완료 시간은 중앙값 약 4.4초·P95 약 5.9초였고 목표 10초 이하는 통과했습니다. 하지만 체감 속도를 더 개선할 여지는 있습니다.

**상세 답변:** SSE는 생성 중 일부 문장을 먼저 표시하지만, 이번 P95는 SSE 첫 토큰 시간이나 완료 시간의 별도 측정이 아닙니다. “SSE 첫 글자가 5.9초 안에 나온다”처럼 해석하지 않습니다. 다음 단계에서는 첫 토큰 시간·전체 완료 시간·검색·범위 판정·생성 구간별 시간을 나눠 병목을 확인하겠습니다.

### 48. [18쪽] 45/45 성공과 테스트 158개면 안정적인 서비스라고 봐도 되나요?

**바로 말할 답변:** 특정 평가 실행과 회귀 테스트를 통과했다는 근거이며, 장기 가용성과 부하 대응까지 검증한 것은 아닙니다.

**상세 답변:** 45문항은 평가 API 호출 성공이고 158개는 당시 자동 테스트 통과 기록입니다. 동시 사용자 수, 분당 처리량, 장시간 오류율, 외부 API 제한 도달 상황은 별도로 측정해야 합니다. 특히 현재 평가 채팅 호출은 순차적으로 실행되므로, P95를 다수 동시 접속 상황의 지연 보장으로 말하지 않겠습니다.

## F. 추천·DB·인증·개인정보

### 49. [7·9쪽] 개인 맞춤 추천은 어떻게 하나요? 협업 필터링인가요?

**바로 말할 답변:** 현재는 다른 사용자 집단의 행동을 학습하는 협업 필터링이 아니라, 사용자의 좋아요·열람 작품과 가까운 작품을 찾는 콘텐츠 기반 추천입니다.

**상세 답변:** 최근 좋아요 10점을 시드로 사용하고, 없으면 최근 열람 5점을 사용합니다. 작품 대표 벡터와 가까운 후보 최대 30개를 가져와 작품 추천은 작가당 한 점씩 최대 3점을 고릅니다. 추천 작가는 후보의 유사도를 합산하고 이미 팔로우한 작가를 제외합니다. 좋아요한 작품의 작가까지 무조건 제외하는 것은 아닙니다.

### 50. [9쪽] 신규 사용자는 추천이 안 나오나요? 왜 평균 취향 벡터를 안 만들었나요?

**바로 말할 답변:** 좋아요가 없으면 최근 열람, 팔로우 작가 작품, 큐레이션·그 밖의 이미지 있는 작품 순서로 보완합니다.

**상세 답변:** 대체 무작위 순서는 사용자와 서울 날짜로 고정해서 새로고침마다 과도하게 흔들리지 않도록 했습니다. 평균 벡터 대신 각 시드와의 가까움을 사용하면 서로 다른 취향이 하나의 평균으로 섞이는 문제를 피하면서 추천 이유가 되는 시드도 표시할 수 있습니다. 그러나 사용자 만족도 실험으로 우월성을 증명한 것은 아니고, 충분한 후보가 있어야 목표 개수를 채울 수 있습니다.

### 51. [9·20쪽] AI 감성 컬렉션과 일반 추천은 무엇이 다른가요?

**바로 말할 답변:** 일반 추천은 저장된 작품 벡터를 중심으로 다음 작품을 고르고, 감성 테마는 관심 기록을 바탕으로 여러 작품을 하나의 분위기·상황으로 묶습니다.

**상세 답변:** 테마 생성은 실제 카탈로그 후보 ID만 사용하고, 테마당 3~8점·작가 다양성·관심 작품 포함 등의 조건을 검증합니다. 사용자별 DB 스냅샷을 재사용하며 의미 있는 관심 변화가 있을 때 다시 만들고 시도 간격은 30분입니다. 모델이 분위기 이름을 만든다는 사실과 사용자에게 정말 좋은 테마라는 평가는 별개라, 품질·선호도 검증은 더 필요합니다.

### 52. [7쪽] 테이블을 왜 22개나 나눴나요? 복잡하지 않나요?

**바로 말할 답변:** 사용자·작품·문서·활동의 수명이 다르고 다대다 연결도 많아서, 중복과 소유권을 명확히 하려고 분리했습니다.

**상세 답변:** 작품 벡터는 목록 조회에 불필요해 별도 테이블로 두고, 문서 청크는 문서와 다른 단위라 분리했습니다. 좋아요·팔로우·열람·컬렉션 작품은 연결 테이블이고 복합 키로 중복을 막습니다. AI 테마 캐시도 사용자가 저장한 컬렉션과 수명이 달라 구분했습니다. 수가 많아도 여러 테이블은 몇 개 컬럼의 연결 구조이며, 기능 확대에 따른 설계 복잡성은 남아 있습니다.

### 53. [7·18쪽] 같은 요청이 두 번 오거나 동시에 저장하면 중복이 생기지 않나요?

**바로 말할 답변:** 좋아요·팔로우·컬렉션 담기는 DB 키와 멱등적인 저장 방식으로 중복을 제한하고, 컬렉션 한도는 행 잠금을 사용합니다.

**상세 답변:** 예를 들어 같은 컬렉션에 같은 작품을 두 번 담아도 복합 PK 때문에 한 행만 남습니다. 계정당 컬렉션 10개·컬렉션당 작품 30점 한도는 동시에 요청해도 검사와 쓰기 사이를 보호하도록 처리합니다. 반면 열람 기록은 재호출할 때 view_count를 늘리는 의도된 동작이므로 모든 POST가 멱등적인 것은 아닙니다. 채팅 중복 저장 방지도 별도 요청 식별자 없이 완전히 해결됐다고 말하지 않습니다.

### 54. [최우선 / 18·20쪽] Firebase를 프론트에서 로그인하면 백엔드는 무엇을 검증하나요?

**바로 말할 답변:** 프론트 로그인 성공 여부를 그대로 믿지 않고, 백엔드가 Firebase Admin SDK로 ID 토큰을 검증한 뒤 UID에서 내부 사용자를 결정합니다.

**상세 답변:** 현재 사용자 ID를 요청 본문이나 임의 쿼리에서 받지 않습니다. 처음 보는 UID는 users에 등록하고 UNIQUE와 재조회로 동시 최초 요청을 처리합니다. 운영은 AUTH_MODE=firebase를 사용해야 하며 개발 모드는 임의 Bearer 토큰을 고정 개발 계정으로 매핑하므로 운영 인증 수준과 다릅니다. 인증과 자원 소유권 확인은 별개의 검사입니다.

### 55. [18·20쪽] 사용자 ID를 안 받으면 남의 데이터 접근이 아예 불가능한가요?

**바로 말할 답변:** 사용자 ID를 토큰에서 결정하는 것만으로 충분하지는 않습니다. 컬렉션 ID 같은 자원 ID에도 소유권을 검사해야 합니다.

**상세 답변:** 서버는 컬렉션 조회·변경 시 해당 컬렉션의 소유자와 인증 사용자를 확인합니다. 최신 배포 A/B 검증에서는 B가 A의 컬렉션을 조회·추가·수정·삭제하려는 요청이 404로 차단됐고 A의 데이터도 유지됐습니다. 따라서 슬라이드의 “접근할 방법 자체가 없음”보다는 “토큰 기반 사용자 결정과 자원별 소유권 검사로 차단”이 정확합니다.

### 56. [9·18쪽] 감상평·생년월일 같은 개인정보가 LLM으로 나가나요?

**바로 말할 답변:** 기능별로 보낼 데이터를 제한합니다. 도슨트는 생년월일을 답변 근거로 쓰지 않고, 취향 소개는 공개 감상평만 제한적으로 사용합니다.

**상세 답변:** 취향 소개에는 좋아요·컬렉션 작품 최대 100점의 정보와 공개 감상평 최근 20편의 각 300자까지를 전달하며, 비공개 감상평·이메일·Firebase UID·생년월일은 넣지 않습니다. 도슨트 질문과 필요한 대화 이력 자체는 답변 생성에 전달됩니다. 공개 작성 동의와 AI 처리 고지는 제품 운영 시 별도로 명확히 해야 하며, 현재 코드의 전송 필드 제한이 개인정보 운영 체계 전체를 대신하지는 않습니다.

## G. MCP·운영·확장·협업

### 57. [최우선 / 4·20쪽] MCP가 뭔가요? REST API가 있는데 왜 추가했나요?

**바로 말할 답변:** 외부 AI 클라이언트가 도구 목록과 입력 형식을 알아보고 호출할 수 있도록 표준 도구 인터페이스를 추가한 것입니다.

**상세 답변:** 앱은 REST를 사용하고, MCP는 /mcp/의 Streamable HTTP로 같은 컬렉션 서비스를 호출합니다. 목록·작품 검색·자동 묶음 조회, 생성·작품 추가·감상 기록 기반 생성의 6개 도구가 있습니다. MCP가 검색 정확도를 높이는 것은 아니며, 사용자 기록 기능을 앱 바깥에서도 활용하게 하는 확장 경로입니다.

### 58. [최우선 / 4·20·21쪽] Claude 같은 실제 AI 비서에서도 연결해 봤나요?

**바로 말할 답변:** 최신 기록에서 확인한 것은 배포 프론트의 실제 Firebase 계정 A/B로 브라우저에서 배포 MCP를 호출한 프로토콜·도구·격리 검증입니다.

**상세 답변:** Claude Desktop 같은 데스크톱 MCP 클라이언트의 실제 연결은 별도로 실행하지 않았습니다. 현재는 Firebase Bearer 토큰을 직접 제공하는 방식이고 외부 클라이언트용 OAuth 로그인·동적 등록은 제공하지 않습니다. 따라서 “표준 전송과 도구를 구현했다”는 것과 “여러 상용 클라이언트에서 로그인까지 연결 검증했다”는 것을 구분합니다.

### 59. [최우선 / 20쪽] 배포에서 어떤 문제가 있었고 어떻게 해결했나요?

**바로 말할 답변:** MCP는 무토큰 요청에서 401이 나와 정상처럼 보였지만, 유효 토큰으로 초기화하니 Host 검사에서 421 오류가 났습니다.

**상세 답변:** MCP_ALLOWED_HOSTS가 로컬 주소만 허용하고 있어서 Railway 배포 도메인이 거절됐습니다. 인증 미들웨어가 먼저 실행되므로 무토큰 검증만으로는 이 오류가 보이지 않았습니다. 허용 Host를 수정·재배포한 뒤 initialize 200, 6개 도구, 실제 계정 A/B 격리를 확인했습니다. 배운 점은 실패 경계뿐 아니라 유효한 요청의 성공 경로까지 검증해야 한다는 것입니다.

### 60. [20쪽] AI가 컬렉션을 마음대로 바꾸면 위험하지 않나요?

**바로 말할 답변:** 앱 안의 컬렉션 채팅은 제안만 만들고 사용자가 확인한 뒤 REST로 저장합니다. 외부 MCP의 쓰기 도구는 실제 저장 동작이라는 점을 구분합니다.

**상세 답변:** 앱 제안에는 실제 카탈로그 작품 미리보기를 주고, 최종 저장 때도 소유권·작품 존재·한도·중복을 다시 확인합니다. MCP 도구에도 명시적 요청에 사용하라는 설명을 두었지만, 서버가 인간의 의도를 독립적으로 증명하는 것은 아닙니다. 외부 클라이언트의 확인 UI와 권한 정책까지 중요하므로 “모든 쓰기는 반드시 우리 앱 확인 버튼을 거친다”고 말하면 안 됩니다.

### 61. [7·18·21쪽] 사용자가 많아지면 지금 구조로 버틸 수 있나요?

**바로 말할 답변:** 현재 평가만으로 동시 사용자 처리량을 확답할 수는 없습니다. 가장 먼저 외부 LLM 호출·DB 쿼리·검색 지연을 나눠 측정해야 합니다.

**상세 답변:** 현재는 제한된 규모의 카탈로그와 순차 평가를 기준으로 했고, 일부 추천 쿼리는 여러 시드와 후보의 거리를 계산합니다. 규모가 커지면 후보 검색·인덱스·사전 계산·캐시·작업 큐·사용자별 호출 제한을 검토해야 합니다. 이미 적용된 기능과 앞으로 검토할 확장 설계를 구분하고, 처리량 숫자는 부하 테스트 후 제시하겠습니다.

### 62. [7·10·18쪽] 운영 비용과 장애는 어떻게 관리하나요?

**바로 말할 답변:** 데이터 임베딩·질문 임베딩·LLM 생성·인프라 비용을 나눠 봅니다. 현재 코드에는 테마 캐시와 재사용 규칙이 있지만 서비스 전체 비용 상한이 검증된 것은 아닙니다.

**상세 답변:** 일부 질문은 분류나 직접 답변으로 생성 호출을 생략하지만, 일반 도슨트는 범위 판정과 생성 등 여러 외부 호출이 발생할 수 있습니다. 따라서 “질문당 LLM 한 번”이나 근거 없는 원 단위 단가를 말하지 않습니다. AI·검색 장애 시에는 503 또는 SSE error로 안내하며, SSE가 끊겼다고 자동 재전송해 중복 답변·저장을 만드는 동작은 피합니다. 사용자별 rate limit·예산·구간별 모니터링은 상용화 보강 항목입니다.

### 63. [11쪽] 다섯 명이 병렬로 개발하면서 통합 문제는 어떻게 줄였나요?

**바로 말할 답변:** 문서 스키마, 검색 결과 Document 형식, API 요청·응답 계약을 먼저 맞췄습니다.

**상세 답변:** 수집 담당은 processed 산출물과 문서 키를, 검색 담당은 page_content와 metadata를, 생성 담당은 구조화 답변을, 프론트는 API 스키마를 기준으로 작업했습니다. 그래도 데이터 승인·실제 배포 코드·환경변수·문서가 어긋나는 문제가 발생했고, 운영 API 재실행으로 찾아냈습니다. 계약을 정했다고 통합 문제가 없어지는 것이 아니라, 어디에서 어긋났는지 빠르게 찾는 기준이 되었습니다.

**개인 기여도 질문 대응:** 자신의 담당 범위·직접 수정한 문제·검증 결과를 실제 커밋과 작업 기록으로 답합니다. 다른 팀원의 결과나 5명 전체의 구현을 개인 성과로 합쳐 말하지 않습니다.

### 64. [최우선 / 21쪽] 시간이 더 있으면 무엇부터 개선하겠습니까?

**바로 말할 답변:** 첫째 거절 상태값의 의미 불일치, 둘째 보지 않은 질문과 실제 입력 trace를 이용한 평가, 셋째 raw 청크 검색을 우선하겠습니다.

**상세 답변:** refused는 UI와 통계에 영향을 주는 API 계약이므로 먼저 고칩니다. 이후 사후 재검색 대신 실제 생성 입력으로 평가하고, 독립 Judge·미사용 질문으로 일반화를 확인합니다. 검색은 정답 청크 라벨 검토 후 키워드 결합·재정렬을 비교합니다. 그다음 실제 외부 MCP 클라이언트 연결과 동시성·비용·운영 관측을 검증하겠습니다. A/B 격리는 최신 배포 기록상 이미 통과했으므로 남은 과제에서 빼는 것이 맞습니다.

### 65. [전체] 이 프로젝트에서 가장 중요한 성과와 한계는 각각 무엇인가요?

**바로 말할 답변:** 성과는 근거 검색부터 출처·저장·배포까지 하나의 서비스로 연결하고, 실패를 단계별로 구분해 수정·재검증한 것입니다. 한계는 제한된 데이터와 평가셋, 남은 상태값 오류, 독립 평가·부하 검증 부족입니다.

**상세 답변:** 종합 43/45와 배포 실제 계정 격리는 현재 범위의 동작을 보여 줍니다. 하지만 이것을 미술 지식 전체의 정확도나 상용 서비스의 완성으로 확대하지는 않습니다. “답을 잘 만든다”에서 끝내지 않고 어떤 자료가 들어갔고 무엇을 확인했는지 남겼다는 점을 성과로 설명하고, 다음 개선 우선순위를 함께 제시하겠습니다.

## 실제 질의응답 연습 순서

시간이 적으면 **2 → 16 → 24 → 27 → 34 → 35 → 37 → 40 → 41 → 43 → 55 → 58 → 59 → 64** 순서로 연습합니다.

답변은 먼저 1~2문장으로 결론을 말한 뒤, 질문자가 더 물으면 구현·수치·한계를 덧붙입니다. “아직 하지 않았다”로 끝내기보다 무엇을 확인했고 다음에 어떤 조건으로 검증할지를 붙입니다.

자주 나오는 세 가지 압박 질문에는 다음처럼 일관되게 답합니다.

- **“그래서 100% 정확하다는 겁니까?”** → “아닙니다. 고정 평가셋과 각 지표의 분모 안에서 확인한 결과입니다. 거절 상태값 두 건과 raw 청크 검색의 미달도 함께 공개했습니다.”
- **“규칙으로 정답을 넣어 점수를 올린 것 아닌가요?”** → “작품·작가 관계에 따른 일반 규칙이지만 같은 평가셋에 튜닝한 편향은 남습니다. raw 검색을 분리 공개했고 미사용 질문 검증이 필요합니다.”
- **“보안이 검증됐다는 근거는 뭡니까?”** → “Firebase 토큰 검증과 자원 소유권 검사를 구현했고 배포 실제 계정 A/B의 특정 교차 접근을 차단했습니다. 이것을 모든 공격에 대한 보안 보장으로 확대하지는 않습니다.”
