# 감상평·다이어리와 화면 성능 개선

## 변경 내용

- 추천 영역을 홈의 소개 영역 다음, 전체 작품 목록 앞으로 이동했습니다.
- 날짜별 감상평을 서버 저장하며 기본 비공개, 공개/비공개 변경은 저장 후 반영됩니다. 공개 글은 감상 피드와 해당 작품 상세에서 조회합니다.
- 캘린더는 글이 있는 날짜에 공개/비공개 아이콘을 표시합니다. 감상평만 쓴 날도 표시하며 작품 감상 수·반복 열람 횟수와 분리합니다. 다이어리 탭에서 날짜별 글을 열어 같은 편집기로 수정·삭제합니다.
- 날짜·월·탭 변경 시 저장하지 않은 글이 있으면 이동 여부를 확인합니다. 저장 중 날짜 이동은 막습니다.
- 기존 로컬 메모는 자동 공개/업로드하지 않습니다. 직접 저장 시 새 다이어리로 옮기고 중복 로컬 메모를 제거합니다.

## 성능 변경

- 감상평 입력 상태를 별도 위젯으로 분리해 키 입력 때 캘린더가 다시 빌드되지 않습니다.
- 상세·유사 작품 요청을 5분 동안 재사용하고 동시 요청을 합칩니다. 맞춤 추천은 30초 동안 재사용하며 좋아요·팔로우·계정 변경·새 열람·강제 새로고침 시 갱신합니다. 요청 보관은 최대 80개입니다.
- 작품 이미지 표시 영역과 화면 배율을 기준으로 Commons 썸네일 크기를 선택합니다. 제공처의 기존 썸네일 URL은 유지하며 이미지 디코딩 크기도 제한합니다.
- 다운로드 진행마다 재빌드하는 로딩 표시를 정적인 자리 표시로 바꾸고 이미지·카드의 다시 그리기 범위를 분리했습니다.
- 공개 피드는 기본 12건, 최대 30건으로 조회하고 커서로 다음 페이지를 읽습니다. SQL 공개 여부/작품/id 인덱스를 포함합니다.

## 운영 적용

1. 운영 담당자가 기존 DB 백업과 현재 migration revision을 확인합니다.
2. 최신 백엔드 코드로 `alembic upgrade head`를 실행해 0007을 적용합니다.
3. AUTH_MODE=firebase와 기존 프로젝트 인증 설정을 확인하고 백엔드·프론트를 배포합니다.
4. 두 실제 계정에서 비공개 글 분리, 공개 피드 조회, 비공개 재전환·삭제, 새로고침 후 캘린더·다이어리 유지까지 확인합니다.

운영 DB 마이그레이션·배포는 이번 로컬 코드 작업에서 실행하지 않았습니다. 기기·네트워크별 실제 FPS와 운영 서버 응답 시간은 배포 후 측정 대상입니다.

## 검증 결과

- 백엔드 전체 288개 통과: 실제 SQL을 사용하는 격리 SQLite 테스트에서 계정 분리, 공개→비공개 전환, 삭제, 월 경계, 작품 필터, 커서 페이지 나누기, 입력 검증을 확인했습니다.
- Flutter 전체 87개 통과, 정적 분석 이슈 없음. 320/390/768/1280/1440px 기존 화면 회귀와 신규 작성·피드 화면 검사를 포함합니다.
- 입력 전후 동일한 캘린더 셀 위젯이 유지되는지 검사했습니다. 동시 상세 요청 2회와 추천 요청 2회가 각각 서버 요청 1회로 합쳐지고, 강제 새로고침·로그아웃 후 갱신되는지 확인했습니다.
- release 웹 빌드 성공. Alembic head는 0007 하나이며 MySQL/TiDB 방언의 전체 offline SQL 생성 성공. DB에는 적용하지 않았습니다.
- 로컬 release 웹 체험 모드에서 작성→공개 저장→캘린더 표시→다이어리 목록→공개 피드→비공개 재전환 후 피드 제외를 직접 확인했습니다. 이는 실제 두 사용자 운영 로그인을 대신하지 않습니다.
